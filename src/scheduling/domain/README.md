# 领域层

**零框架依赖。** 不 import pandas、ortools、fastapi、sqlite 中的任何一个。
判断标准：换掉求解器、换掉数据库、换掉界面，这一层一行都不用改。
`tests/domain/` 里有一条自动化断言在守这条线。

## 为什么这些概念值得建成类型

这个项目的业务规则经过十几轮澄清，期间推翻过 7 条推断。多数错误的形式都一样：
**某个业务概念在代码里是字符串或元组，于是两处对它的理解可以悄悄分叉。**

| 概念 | 曾经的形态 | 出过什么事 |
|---|---|---|
| 转场次数 | 两处各自实现 | 求解算 `distinct−1`、体检算实际事件，同一份排班报出 19 和 25 |
| 学生撮 | `(校区, 程度, 层级)` 元组 + 年级推全科 | 把刚降级掉的 H2 从后门放回来 |
| 期位 | 「段次」和「周」两个字段 | 两个场景各写一套降级逻辑，其实是同一个动作 |
| 坐标 | 裸经纬度 | 未知坐标系静默当 WGS-84，偏差几百米且不报错 |
| 权重 | 裸 dict | 改键名没同步，KeyError 崩掉报告；调三轮权重不生效 |

所以这一层的价值不在"分层好看"，在于**把业务语言变成编译期/构造期就能挡住错误的类型**。

## 目录

```
model/      实体与值对象 —— 业务语言的载体
  timeslot.py           时段（半开区间，端点相接不算重叠）
  timetable.py          时段表（课间阈值从表本身推导，不用填参数）
  curriculum.py         产品↔科目↔年级、程度、层级
  period.py             期位（一个变量表达两个场景）
  cohort.py             人群与报读组合 ⚠️ 人群 ≠ 同一批人 ≠ 全科
  team.py               团队
  instructor.py         指导员
  venue.py              中心、教室、坐标（datum 必须显式）
  academic_calendar.py  学年日历

policy/     可配置的业务规则
  adjacency.py    连堂三档：同半天 > 跨午休 > 分散
  travel.py       转场口径（A→B→A = 2）与保守兜底
  degradation.py  降级链：挪期位 ≠ 排不上
  golden_hours.py 黄金时段（条件性硬排除，需与营业时段取交集）
  weights.py      权重（按键覆盖，未知键报错，生效值必须打印）

service/    跨模型的业务逻辑
  readiness.py    数据就绪度 —— 顶部常驻告警条的数据源

repository.py     仓储接口（Protocol），依赖倒置的边界
```
