### 2.1 `slots.py` —— 时段代数

```python
parse_slot("08:10-10:10")  → (490, 610)        # 转成当天分钟数
overlaps(a, b)             → a[0] < b[1] and b[0] < a[1]
make_gap_counter(slots)    → gap_count(a, b)   # 两个时段之间还塞得下几个时段；0 = 相邻
adjacency_waits(slots)     → [10, 20, 50, 60, 90]
derive_adjacency_limit()   → 20                # 见下
```

**自动推导课间阈值**【已实现 · 已验证】：把所有相邻等待时间排序，找最大的**比值跳变**（20→50 是 2.5 倍），分界点前的算课间、后的算休息。当前时段表推出 **20 分钟** —— 10/20 是课间，50/60/90 是休息。

好处：换一套时段表不用重新填参数。坏处见 §5 R2 —— 它被误用成了"连堂的硬门槛"。

### 2.2 `travel.py` —— 转场判定

```python
Travel.minutes(a, b)        # 通行分钟
Travel.km(a, b)             # 里程
Travel.source(a, b)         # "地图" | "估算" | "档位" —— 报告里要如实标注
Travel.acceptable(a, b, available_minutes)
Travel.tier(a, b)           # 同校区 | 同区域 | 跨区域
```

数据来源优先级：`travel.csv`（地图实测）> 经纬度直线估算 > 档位兜底。

**兜底必须保守**【已实现 · 修复过的 bug】：
```python
# 区域不明的一律按跨区域算。两个 None 相等就当成"同区域"的话，
# 缺数据反而会放宽约束 —— 兜底应该保守，不该更松。
ra, rb = self.region_of.get(a), self.region_of.get(b)
if ra and rb and ra == rb:
    return "同区域"
return "跨区域"
```
曾经 `solve()` 传了空的 `region_of`，`None == None` 让全部中心读成"同区域"（40 分钟而不是 70 分钟），把不可能的转场判成可行。

### 2.3 `solver.py` —— CP-SAT 建模

**变量**：每个团队一组 `(时段, 主指导员, 指导室)` 的布尔/整数变量。

**子问题切分**：按 `(段次, 周)` 分组分别求解。
> ⚠️ 这正是 §5 R1 的病根 —— 批次在日期上重叠且共用教师，分开求解检不出跨批次撞车。

**建模手法**：
- 硬约束直接建模（H1 一人一时段、H2 冲突口径、H3 教室上限、H4 资质）
- 转场用 `AddAllowedAssignments` 表约束，把可行的 `(时段a, 中心a, 时段b, 中心b)` 组合枚举成白名单
- **对称性破除** —— 同一组平行班之间强制序关系。【已验证】惩罚从 37244 降到 14334
- 求解 hint 热启动（repair 模式下用原排班当初始解）

**默认权重**【已实现】：
```python
DEFAULT_WEIGHTS = {
    "未排上团队": 100000, "连堂不相邻": 60, "硬约束倍数": 50,
    "跨中心一次": 800, "每公里转场": 6, "课表空档一段": 8,
    "工作量峰值": 30, "与原排班不同": 0,
}
```

> **【已验证】的配置陷阱**：`config/rules.yaml` 的 `权重` 块**整块覆盖**这张表。曾连续三轮调 `跨中心一次`（20→150→800）完全不生效 —— 因为配置文件里还是 20。发现方式：报告里 `跨中心 460 = 23 × 20`，不是 `× 800`。
> **必须做**：加载配置后打印实际生效的权重表。
>
> 另一条：权重键改名（`工作量方差` → `工作量峰值`）没同步到 `health.py`，直接 KeyError 崩了报告。现在所有权重读取一律用 `.get()`。

### 2.4 `health.py` —— 体检

对**任意**一份排班（手工的或求解出的）算：H1/H2/H3 违规清单、S1 连堂达标率、S2/S3 转场次数与里程、总得分。

用途有三个：
1. 给现有手工排班打基线分
2. 验证求解结果真的满足硬约束
3. rebuild 前后对比，量化改善幅度

**H2 双向判定**【已验证 · 修复过的 bug】：时段存在重叠（13:30-15:30 × 14:00-16:00），只做 `if p1 < p2` 会漏掉 8 处反向违规，必须 `if p1 != p2`。

> ⚠️ H2 已由硬约束降级为软约束 S8（缺陷 R7，见业务需求 §3.1）。体检报告里它应当从"违规清单"移到"扣分项"，并按受影响学生数计权，而不是按"存在并发产品对"计数。

### 2.5 `output.py` —— 输出

写 5 个 sheet：`总览` / `排班明细` / `看板` / `老师课表` / `问题清单`。

**明细 sheet 的列名与源数据兼容** —— 输出可以直接当输入喂回体检，形成闭环。

### 2.6 `mapapi.py` + `coords.py` —— 地图

| | `osm`（默认） | `amap`（高德） |
|---|---|---|
| 要 key | **否** | 是 |
| 坐标系 | WGS-84 | GCJ-02（火星坐标） |
| 服务 | Nominatim 地理编码 + OSRM `table` 矩阵 | 高德地理编码 + 路径规划 |
| 调用次数 | N 次编码 + **1 次**矩阵 | N 次编码 + N 次矩阵 |
| 国内 POI 覆盖 | 一般，商场/门店名常查不到 | 好 |

用户要求"不要必须高德 key，开源地图即可，1km 误差可接受" → **默认走 OSM，完全免 key**。

**坐标自动反查**【已实现】：「百花科学」是内部中心名，地图上没这个 POI。按由细到粗试四种问法，命中就停：
1. 地址列的详细地址
2. 城市 + 中心名（深圳百花科学）
3. 城市 + 区域 + 校区名（深圳福田区百花）
4. 城市 + 校区名（深圳百花）

校区名通常是真实地名，命中率最高。同校区的多个中心共用查询结果，少调几次也保证坐标一致。命中的问法写进「定位依据」列，方便逐条核对。

**范围校验**：落在城市范围外的直接丢弃，**宁可留空也不写错坐标** —— 地图服务对模糊查询经常返回外省同名地点，混进来会把全城距离算歪且不报错。

**坐标系混用**【已验证】：两个坐标系在深圳差 **300–700 米**。一个 GCJ 点配一个 WGS 点直接算距离会凭空多出几百米，这是国内地图数据最常见的坑。`centers.csv` 有「坐标系」列记录来源，读表时统一折算到 WGS-84，`tests/test_coords.py` 专门盯住。

## 3. 网页服务层【计划】

### 3.1 技术选型与理由

| 选择 | 理由 |
|---|---|
| **FastAPI** | Python，直接 import `engine/`，无跨语言胶水 |
| **Jinja2 + HTMX** | 排班是"表单 → 等待 → 看结果"的流程，不需要 SPA。**不引入 Node 工具链**，内网部署少一层构建依赖 |
| **SQLite** | 单机内网，并发是个位数。省掉一个数据库容器 |
| **文件系统存产物** | 上传的 xlsx、输出的 xlsx 直接落盘，SQLite 只存路径和状态 |
| **无认证** | 【用户定案】内网部署，谁能访问谁能用 |

### 3.2 页面与流程

```
⓪ 初始化引导（首次部署时走一遍）
   ├─ 导入中心清单 → 自动反查坐标 → 手动补齐反查不到的
   ├─ 导入指导员名单 → 配置可教产品 / 可去中心 / 不可用时段
   └─ 填学年日历（寒暑假、春秋季的起止日期）

① 上传 / 新建任务
   └─ 上传团队清单 xlsx，或从上次任务复制

② 配置
   ├─ 选场景：寒暑假 / 春秋季
   ├─ 时段表（按场景带默认值，可改）
   ├─ 连堂规则与优先级
   ├─ 地理判定：时间 / 距离，安全余量
   ├─ 单人单日上限：节数 / 中心数
   ├─ 黄金时段：勾选时段（默认上午两档）+ 勾选星期（默认周六日全天）
   ├─ ☑ 允许促销班占黄金时段
   └─ 权重滑块（显示实际生效值 —— 见 §2.3 的陷阱）

③ 触发求解 → 后台任务
   └─ HTMX 轮询进度：已用时 / 当前最优解 / best_bound / 状态

④ 结果
   ├─ 在线看板（HTML 表格，就是截图那张）
   ├─ 冲突 & 未排清单
   ├─ 与基线对比（手工排班 vs 求解结果的分数差）
   └─ 下载 xlsx

⑤ 后台配置（长期维护，独立于单次任务）
   ├─ 中心管理：地址、坐标、教室数、区域
   ├─ 指导员管理：批量编辑 + 单个编辑
   └─ 学年日历
```

### 3.2.1 顶部常驻告警条 【用户定案】

```
┌──────────────────────────────────────────────────────┐
│ ⚠ 3 个中心还没有坐标，跨中心时间只能粗判 → 去补齐      │
└──────────────────────────────────────────────────────┘
```

固定挂在页面顶部，数据补齐了才消失。触发条件至少两类：

| 触发 | 后果（如果不管） |
|---|---|
| 有中心缺坐标 | 转场时间退化成同校区/同区域/跨区域三档粗判，"赶不赶得及"基本失效 |
| 有指导员缺配置 | 资质和可用性约束落空，可能排出他去不了的中心 |

> **为什么必须是常驻告警而不是一次性提示**：缺坐标**不会报错**，求解照样出结果，只是悄悄退化。这种沉默的降级最危险 —— 用户拿到一份看起来正常的排班，实际上路上时间全是猜的。所以要一直喊到补完为止。

### 3.2.2 坐标手动补录 【用户定案】

自动反查（`geocode_centers.py`，见 §2.6）覆盖不到的中心，给一个人工入口：

```
中心：石厦文学
  自动反查：✗ 未命中
  [ 在地图上选点 ]  ← 新窗口打开地图，用户找到位置
  经纬度：[ 114.0579, 22.5431 ]  ← 从地图复制粘贴
  坐标系：( ) WGS-84   (•) GCJ-02（国内地图默认）
```

**坐标系必须让用户选**，且默认 GCJ-02 —— 国内主流地图（高德、腾讯、百度）复制出来的都是火星坐标，直接当 WGS-84 用会差 300–700 米。系统读表时统一折算（`coords.py`）。

### 3.2.3 指导员配置页 【用户定案】

**批量编辑 + 单个编辑**两种入口。批量的典型场景：整个校区的老师统一加一条"不可用时段"、一批新老师统一设可教产品。

```
姓名 | 可教产品 | 可去中心/区域 | 不可用星期/时段 | 单日最多节数 | 单日最多中心数 | 不可调整
```

排班时直接读这张表算可行性，不在任务配置里重复一遍。

### 3.3 任务状态机

```
PENDING → RUNNING → {FEASIBLE_TIMEOUT | OPTIMAL | INFEASIBLE | ERROR}
```

**为什么必须异步**【已验证】：求解在 `不限` 候选池下 **140 秒仍停在 FEASIBLE**，没收敛。HTTP 请求扛不住，必须后台跑 + 轮询。

**必须如实汇报求解状态**：`FEASIBLE`（有解但没证明最优）和 `OPTIMAL`（证明了最优）是两回事，界面上要分开显示，并给出 `best_bound` 让用户判断还有多少改善空间。把 FEASIBLE 说成"排好了"是误导。

### 3.4 数据模型（SQLite）

```
task(id, 名称, 场景, 状态, 配置json, 输入文件路径, 输出文件路径,
     创建时间, 开始时间, 结束时间, 求解状态, 目标值, best_bound, 错误信息)

center(名称, 校区, 区域, 地址, 经度, 纬度, 坐标系, 定位依据, 教室数)
instructor(姓名, 可教产品json, 可去中心json, 不可用时段json,
           单日最多节数, 单日最多中心数, 不可调整)
calendar(批次名, 起始日期, 结束日期, 期位A日期json, 期位B日期json)
```

`task.配置json` 直接存 JSON —— 规则字段还在演进，建成表结构会天天改 schema。
后三张表是**长期主数据**，独立于单次任务，所以建成正式字段：它们要支持列表页、批量编辑和"缺配置"查询（告警条要用）。

### 3.5 部署

```
公司内网服务器
  └─ Docker 容器
       ├─ FastAPI (uvicorn)
       ├─ 后台任务 worker（同进程线程池即可，并发个位数）
       └─ 卷挂载：data/（上传与产物）、config/（规则与坐标表）
```

`config/centers.csv` 和 `config/travel.csv` 挂在卷里，跑一次地图工具生成后长期复用，**排班过程完全离线**，不需要网络也不需要 key。

**Windows 控制台编码**【已验证 · 修复过的 bug】：Windows 上 Python 的 stdout 默认 cp1252，打印中文直接 `UnicodeEncodeError`。修在**代码**里而不是 CI 的环境变量里，这样 Windows 命令行用户也受益：

```python
try:
    from console import force_utf8
except ImportError:          # console.py 缺失时也不该崩 —— 它只是 6 行标准库
    def force_utf8():
        for _stream in (sys.stdout, sys.stderr):
            try:
                _stream.reconfigure(encoding="utf-8", errors="replace")
            except (AttributeError, ValueError, OSError):
                pass
```

配套 5 个回归测试用 `PYTHONIOENCODING=cp1252` 复现原故障。

| **R3** | 连堂配对优先级未实现 | `solver.py` 目标函数 | 数学+语文 / 数学+英语 / 语文+英语 三档权重 |
| **R4** | 转场计数两套口径（求解 `distinct−1` vs 体检"实际事件"） | `solver.py` 的 `_travel`、`health.py` | 统一到"相邻课之间实际发生的中心变更"，`A→B→A` = 2 |
| **R5** | 时段表是单一列表，表达不了"春秋季周五只开一档" | `config/rules.*.yaml`、`data.py` | 改为 `场景 → 星期 → 时段列表` 的嵌套结构 |
| **R7** | **H2 被建成硬约束**，实际是软约束 | `solver.py`、`health.py` | 【重大】见业务需求 §3.1。原表 40% 的"违反"是有意为之 —— 教室和时段容量不够，且并非所有学生都读全科。改为软约束 S8，惩罚正比于受影响学生数。**很可能是求解器过度约束、不收敛的根因之一**，应最先验证 |
| **R6** | **期位与降级链缺失** —— 无「期位」维度、无「挪到另一个期位」动作、无「学生撮」建模对象 | `inputs.py`、`solver.py`、`output.py`、配置 | 见业务需求 §1.5、§4.5。三块工作：① 新增 `学生撮 = (校区, 程度, 团队类型)` 及其应上科目集合；② 给团队加**期位变量**（两个场景共用，渲染成"第一期/第二期"还是"周六/周日"是输出层的事），状态从两态扩成「本期位排上 / 挪到另一期位 / 排不上」三态；③ 目标函数加入严格惩罚序 `已连堂 < 本期位内不连堂 < 挪期位 << 排不上`，外加期位延续性惩罚 |

**修复顺序建议**：**R7**（先把过度约束解开，否则后面所有实验的结论都建立在一个错误模型上）→ R4（口径统一，否则任何对比都不可信）→ **R6**（引入学生撮和期，是 R2/R3 的载体）→ R2 + R3（连堂规则，判定单位就是学生撮）→ R5（场景支持）→ R1（依赖用户提供起始日期，可最后做）。

> **期位这个抽象让 R6 比原先估计的小了一圈。** 用户澄清「暑假第一期平移到周六、第二期平移到周日」之后，「期」和「星期」塌缩成同一个维度，两个场景不需要两套降级逻辑 —— `拆到周六周日两天` 和 `推到第二期` 是同一个动作。模型里只加**一个期位变量**，不加两个。
>
> **R6 仍是本轮工作量最大的一条，也是最核心的一条。** 现有模型只认「团队」，而用户描述的全部排课痛点（三门课能不能同一天上完、排不下推到第二期）都是围绕**一撮学生**说的。不先把这个对象建出来，R2 和 R3 就只是在团队两两之间打补丁，解决不了"这个 S9 学生五门课怎么排"的原始问题。

## 6. 施工计划

| 阶段 | 内容 | 交付 |
|---|---|---|
| **P0** | 归档桌面端：`apps/` `packaging/` `licensing/` → `legacy/`，CI 停掉桌面构建，只留测试 | 仓库瘦身，CI 变快 |
| **P1** | 修 R1–R7 七个缺陷 + 回归测试（R7 先做，R6 为主体） | 内核与业务定案一致 |
| **P2** | FastAPI 后端：任务 CRUD、异步求解、进度查询、文件上传下载 | API 可用，能用 curl 跑通全流程 |
| **P3** | Jinja2 + HTMX 前端：初始化引导、顶部告警条、中心/指导员/日历三个配置页、上传、配置、进度、看板、下载 | 网页可用 |
| **P4** | Dockerfile + docker-compose，内网部署文档 | 一条命令起服务 |

**P1 必须在 P2 之前** —— 内核口径不统一的话，网页上展示的数字本身就是错的。

> **repair 模式的地位被抬高了。** 用户定案「按已报名人数排满、不预留空位，后来的学生等空缺」之后，repair 成了**接纳新生的唯一通道**，而不是"学期中途才用的补丁"。人数每周都在变，重排是日常操作。这意味着 repair 必须**跑得快**（不能像 rebuild 那样 140 秒不收敛）且**改动小**（不能因为多了 3 个学生就把全校课表翻一遍）。P1 里要为它单独设验收标准。
