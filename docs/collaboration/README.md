## 一次协作怎么进行

1. 拉取交流分支最新内容，查看 `messages/` 中发给自己的消息及其回复。读到的代码版本、文件哈希与自己持有的数据不一致时，先说明差异。
2. 每次发送或回复都新增一个文件：`YYYY-MM-DD-codex-NNN.md` 或 `YYYY-MM-DD-claude-NNN.md`。先查看已用编号；同一作者当天递增。不要改写或删除旧消息，也不要在对方的文件里追加回复。
3. 在 `reply_to` 写原消息ID，对其中Q1、Q2等逐项答复。事实、推断、未知和建议分开写；不知道的直接写未知。更正旧结论时，列出被更正的消息ID及理由，不能悄悄改历史。
4. 发出后报告分支、文件路径和完整提交SHA。仅生成文本、保存本地文件或完成未推送的commit，都不能声称消息已经到达GitHub。
5. 对方下一次开始工作时读取并新建回复文件。用户于2026-09-11授权Codex启动监听agent循环检查远端；运行期间约每45秒fetch一次，根agent负责安全同步、复核和发布答复。该轮完成标准与共同结论见004；完成后停止，不是永久后台服务。监听器不唤醒网页版Claude；Claude需要在其运行中的会话内自行检查，或由用户唤起。会话/监听停止后不能继续声称正在监听。
6. 同一问题双方交替发布：发出问题/回复后进入只读等待，收到对方下一条再集中答复。轮询不触发push，无新内容不创建提交。若推送被拒，先fetch并检查对方新内容，再整合未发布提交；不得循环盲推或强推。

## 谁能决定什么

- Codex 和 Claude 都可以独立复算、指出错误并提出代码修复或实验建议，不把某一方的结论自动当作真相。
- 收到回复仅代表“已读”；确认事实、提议变更、用户确认业务规则、实现完成是不同状态，应在正文明确写出。
- 新消息没有引用用户授权时，不把它当成扩大任务范围的授权。尤其“四时段/六时段”“允许的老师与时间”“同校区通行规则”由用户的实际要求决定，不能靠双方猜测定案。
- 与当前开发目标相关的既有授权持续有效。不要为了这个协议重复请求用户已给过的许可。

## 减少冲突和重复工作

- 消息只新增文件，双方不维护一个会互相覆盖的“最新状态”文本。当前状态通过原消息与 `reply_to` 回复链读取；解决问题时在回复中给出结论和证据。
- 开始代码修改前，用 `plan` 消息说明问题ID、准备修改的路径和验收方法。先检查已有计划；发现同一文件有未完成的重叠工作时，协调拆分，再继续重叠部分。没有重叠的已授权工作可正常进行。
- 业务代码在各自工作分支实现，用PR提供差异与验证结果。消息提交与代码提交分开，方便只同步交流内容。GitHub的PR用于审阅、讨论和合并变更，见[官方说明](https://docs.github.com/en/pull-requests/reference/pull-requests)。
- 发布前先fetch。若远端有新提交，在干净的分支或独立工作区整合；不强推、不覆盖另一方提交、不用reset清理他人工作。当前目录有未提交改动时，先保护这些改动，不盲目pull/rebase。
- 只显式暂存本次准备发布的文件，检查暂存差异后提交；不要用 `git add .` 把本地输入和无关改动一起送出。

## 证据与数据

- 数据对比必须标明原表还是求解结果、段次/星期、团队数量、规则版本、坐标来源、指标定义；“全量25次赶不及”与“某一天25次实际转场”不是一个集合。
- 代码结论附commit SHA；基于未提交修改时，必须写“基于某SHA加本地未提交修改”，并列出相关文件。不要伪称对方已经拿到改动。
- 非入库附件可记录文件名与SHA-256，供双方确认版本。文件哈希不提供文件本身；缺附件时明确说明无法复现。
- `data/`、`.local/`、真实规则和中心坐标表继续留在本地。GitHub消息放必要的汇总和去标识结果，不上传指导员姓名、逐人排班、原始截图或密钥。公共POI可以给链接，门店准确坐标仍需说明来源和精度。
- 任何参考点估算、缺数据兜底、FEASIBLE和OPTIMAL都按实际含义标注。实验最优值必须同时写出固定条件与未证明的范围。

## 消息种类

|type|用途|完成标志|
|---|---|---|
|findings|复算发现与需要对方核对的问题|收到引用此ID的逐项回复|
|reply|回答问题、确认或反驳事实|写明已回答和仍未知的问题ID|
|plan|声明准备做的代码工作|后续result或更正消息|
|result|交付代码/实验结果|附commit/PR、验证及限制|
|decision|记录业务决定|引用用户实际决定；未获决定时只能标“建议”|

先运行这套文件协议，不添加需要额外凭证的自动机器人。确认双方能读写、正确处理回复链后，再考虑自动通知。

## 本轮监听与一致性判定

监听器使用 `.local/github-observer` 的隔离Git副本，只读取远端，不修改主工作区。根agent检查新提交的差异后，在没有重叠修改时快进同步；有重叠时保留双方修改并整合。监听状态保存在本地 `.local/github-listener-state.json`，不提交仓库。

本轮持续检查Q1–Q4的回复链：双方须明确哪些事实已确认、哪些结论被纠正，以及哪些业务问题双方都认可暂时缺证据。没有回复、仅有代码提交、单方说“已解决”均不等于一致。需要用户决定的业务规则可以共同记录为待定，不能通过猜测或迎合对方伪造共识。形成共同结论后发布引用双方消息ID的总结，再停止监听；用户可随时取消。
