1. 段次3原排班用4时段，但solved3h求解结果实际用6时段，“只有午休能转场”不适用于求解结果。

一、两个数字不矛盾，是不同口径
--------------------------------------------------------------------------------

  96 次  = 原表全量。4 个段次 × 多个星期几累计，661 行。← Codex 算的
   8 次  = 「段次3 · 星期五」这一天，106 行。         ← 我用的基线
  25 次  = 同一天，求解器排出来的结果。

段次3 是我拿来做对比的单个子问题：最小、最干净，而且这一天只有 4 个时段
（08:10 / 10:30 / 14:00 / 16:20），间隔 20 / 90 / 20 分钟 —— 只有中午那
90 分钟来得及跨中心，所以转场合不合理一眼能判断。


二、原表 96 次转场的完整拆解
--------------------------------------------------------------------------------

按 (段次, 周) 分组，一个组就是「某位老师的某一天」：

    段次      周        团队    老师   跨中心转场
    ------------------------------------------------
    段次1    星期六      200     87       39
    段次2    星期三       71     40       19
    段次4    星期五      175     62       14
    段次2    星期五       84     48       12
    段次3    星期五      106     55        8    ← 本次对比用的
    段次1    星期二       14      9        3
    段次1    星期日        2      1        1
    段次2    星期六        8      6        0
    不分段   星期三        1      1        0
    ------------------------------------------------
    合计                 661              96

密度最高的是段次1 星期六：87 位老师里 39 次转场。


三、段次3 这一天的对照（同一把尺子量的）
--------------------------------------------------------------------------------

                          原排班（手工）      求解器
    H2 同撮学生撞产品      58 对              0
                          涉及 75% 的团队
    赶路来不及             1 次               0
    编程双语真连堂         42%                62%
    跨中心转场             8 次               25 次
    平均每次转场里程       8.0 km             8.0 km
    老师当天只在一个中心   85%                65%
    违规明细条数           95                 28

「真连堂」= 两节课中间不夹别的课，且学生等待 <= 20 分钟。
20 分钟这个阈值是从时段表自动推算的：所有相接组合的间隔是
10/20/50/60/90 分钟，20 -> 50 是最大跳变（2.5 倍），所以 10/20 算课间、
50 以上算休息。跨午休（90 分钟）不算「挨着」—— 教培不是托管，午休家长
要把孩子接走，跨午休等于家长跑两趟。


四、⚠ 重要：这两列不是同一道题
--------------------------------------------------------------------------------

原排班能只跑 8 次转场，是因为它放任了 58 对 H2 冲突（75% 的团队撞产品）。
产品可以随便塞进任何时段，老师自然不用跑。

求解器被要求 H2 归零，产品就被钉死在特定时段，能去教的人也被连带限死，
转场压力必然上升。

所以多出来的 17 次转场里，有多少是「修好 H2 的必然代价」、有多少是求解器
没搜好，目前还没验证。

验证方法：把 H2 从硬约束降成软约束重跑一次。
  - 如果转场掉到 8 次左右 -> 证实是结构性代价，不是求解器的问题
  - 如果还是 25 次 -> 那才是求解器需要继续优化

如果 Codex 从分析原表的角度能给出独立判断，正好可以互相印证。


五、已知的求解器局限（不遮掩）
--------------------------------------------------------------------------------

1. 140 秒返回 FEASIBLE 而不是 OPTIMAL —— 没有收敛到最优。
   候选老师池的大小直接决定能不能算完，实测（段次3，106 团队）：

       不限  每团队 31 个候选  ->  140 秒收敛不了，调权重也没用
       就近  每团队  9 个候选  ->  当前默认，无团队排不上
       历史  每团队  3 个候选  ->  2.3 秒跑到最优，但 15 个团队排不上

2. 单日最多中心数 = 1 时转场能到 0 次、100% 单中心，但有 18 个团队排不上。
   当前默认是 2。

3. 转场判断目前全是「同校区 / 同区域 / 跨区域」三档粗判 —— 中心经纬度还
   没补。补上之后（tools/geocode_centers.py，不需要 key）会换成真实驾车
   时间，那时才能判断这 25 次里哪些是真离谱、哪些其实就在隔壁。

七、本地复算命令
--------------------------------------------------------------------------------

    python tools/health_check.py solved3h.xlsx \
           --config config/rules.yaml --sheet 排班明细

    python tools/schedule.py 原表.xlsx --config config/rules.yaml \
           --sheet 20240716154132910_54 --段次 段次3 --out 我的结果.xlsx

原表全量（4 个段次，每个子问题最多 140 秒）：

    python tools/schedule.py 原表.xlsx --config config/rules.yaml \
           --sheet 20240716154132910_54 --out 全量结果.xlsx

    python tools/geocode_centers.py
